# 관광권역 평가·근거 표시 계약

갱신일: 2026-09-21 · 상태: **지표와 모형 검증 전**

후속 구현: [논문 기반 계산 기능](research/scoring-implementation.md)을 추가했다. 계산 코드는 구현되었으나 지역 지표·전문가 가중치의 실증 검증은 아직 수행하지 않았다.

이 문서는 현재 앱의 점수·가중치·근거 표시를 규정한다. 기존 `DESIGN.md`의 숫자 예시나 초기 가중치와 충돌하면 이 문서를 적용한다.

## 1. 현재 구현과 해석

| 항목 | 현재 허용하는 표시 | 금지하는 해석 |
|---|---|---|
| 데모 종합점수 | 합성 관측값을 공통 모듈로 계산한 값과 `예시 데이터 · 정책 판단 금지` 표시 | 실측·검증된 분석 결과 |
| 라이브 권역점수 | 독립 권역 입력이 없으면 `산출 대기` | 시 전체 방문자나 POI 수를 권역 성과로 환산 |
| 지표별 점수 | 데모는 합성 입력·정규화·기여분 공개. 라이브 입력이 없으면 `지표 근거 미등록` | 총점에서 숫자를 빼서 만든 가짜 세부점수 |
| 가중치 | 데모는 임시 동등가중치/실험용 AHP, 라이브는 `미확정` | 초기 30·25·20·15·10%나 실험용 입력을 검증된 비율로 사용 |
| 데이터 품질 | 모형 검증 상태, 출처, 기간, 단위, 분모, 실제 계산한 가중 자료 확보율 | 근거 없는 ‘신뢰도 48점’, 이를 ‘확보율 48%’로 재명명 |
| 추천 권역 | 명시적 검토 의견이 있는 경우에만 표시 | 배열 첫 항목이나 사용자가 클릭한 권역을 자동 추천 |
| 자료 기준 | 방문자 자료 기간과 스냅샷 발행일을 분리 | 최근 발행한 과거 자료를 최신 관측이라고 표시 |
| 미확인 건수 | 미집계는 `null`/`미집계` | 미집계 상태를 `0건`으로 표시 |

레거시 스냅샷의 `potentialScore`와 `confidenceScore` 필드명은 저장 형식 호환을 위해 남겨둔다. 필드명이 미래 성장확률·통계적 신뢰도를 정의하는 것은 아니다. 새 연구 모형을 구현할 때 별도 버전과 명시적 스키마로 이전해야 한다.

## 2. 제안하는 평가체계

| 영역 | 평가 대상 | 추가 확보가 필요한 근거 |
|---|---|---|
| 관광자원 기반 | 테마에 적합한 자원과 운영 조건 | 실제 운영 확인, 테마 적합성 기준 |
| 체류·지역소비 지원 여건 | 숙박·식음·지역 사업체 연결 | 영업시간·참여 의사·실제 이동 |
| 권역 내 이동 연결 | 주요 지점 간 이동 조건 | 경로·교통수단·시간표 |
| 관광약자 이용 여건 | 이용자 유형별 연속 동선과 서비스 | 현장·당사자 검증 |
| 주민·환경 여건 | 주민 생활과 환경 부담 | 주민조사·관리 기준·현장 관측 |

이는 문헌을 참고한 우리 설계안이다. 방문량·체류시간·관광지출은 별도 성과지표로 관리하고, 여건 점수에 현재 인기와 같은 개념이 중복 반영되지 않게 검토한다.

### 논문과 우리 설계를 구분한다

- [Park & Yoon (2011)](https://onlinelibrary.wiley.com/doi/10.1002/jtr.804): 델파이와 AHP를 이용한 지표 개발 절차의 근거.
- [Hoang et al. (2018)](https://www.mdpi.com/2071-1050/10/9/3097): 자원과 이용·지원 여건을 다기준으로 평가하는 근거.
- [Darcy & Dickson (2009)](https://opus.lib.uts.edu.au/bitstream/10453/10091/1/2008005505.pdf): 접근 요구와 연속적인 관광 경험을 검토하는 근거.
- [Greco et al. (2019)](https://link.springer.com/article/10.1007/s11205-017-1832-9): 가중치·집계 방식·민감도에 따른 해석 한계의 근거.

구체적인 비율·정규화 기준·필수조건은 우리 목적과 데이터에 맞춰 결정하고 검증해야 한다. 전체 서지와 확인 범위는 [논문 근거 설계안](research/scoring-literature.md)에 정리했다.

## 3. 실제 점수 기능을 추가하기 위한 완료 조건

1. 지표마다 원자료·단위·분모·공간·기간·좋은 방향·결측 처리·정규화 기준을 정의한다.
2. 지역 실무자·주민·접근성 당사자를 포함해 지표의 내용 타당성을 검토한다.
3. 점수 척도를 보여준 뒤 AHP 등 명시한 방법으로 가중치를 조사한다. 조사 전에는 확정값을 만들지 않는다.
4. 구현된 공통 계산 모듈에 검토한 실제 자료를 연결한다. 현재 데모의 지도·비교·상세·보고서는 동일 모형/자료 버전의 결과를 읽는다. 운영 DB 평가 이력 저장은 후속 작업이다.
5. 결측은 0점으로 넣거나 권역별로 가중치를 재배분하지 않는다. 공식 점수를 보류하고 필요하면 계산상 범위를 보여준다.
6. 필수 이용조건과 심각한 환경 부담은 총점과 별도 표시한다. 조사 완료를 이용조건 충족으로 바꾸지 않는다.
7. 가중치·정규화·누락자료의 변경으로 순위가 어떻게 달라지는지 검토한다.
8. 모형 버전·자료 버전·평가 시각·현장 검증 이력을 저장하고 보고서에 포함한다.

## 4. 후속 데이터 구조 제안 — 아직 운영 DB에 적용하지 않음

| 엔터티 | 필요한 정보 |
|---|---|
| `indicator_definitions` | 정의, 단위, 방향, 출처, 근거 논문, 정규화 기준, 버전 |
| `evidence_observations` | 값, 공간 범위, 자료 기간, 관측/대리/추정, 조사 범위, 원자료 참조 |
| `evaluation_models` | 선정 지표, 가중치, 조사 방법, 필수조건, 모형 버전 |
| `evaluation_runs` | 권역, 모형·자료 버전, 결과, 결측, 계산상 범위 |
| `field_observations` | 이용자 유형, 동선, 항목별 충족/미충족/미확인/해당 없음, 확인일 |
| `report_versions` | 고정 평가 결과와 과제 상태, 작성일, 보고서 버전 |

현재 `validation_tasks`는 업무 진행과 메모를 기록하는 MVP 구조다. 이 테이블의 완료 상태만으로 지표의 현장 관측값을 자동 생성하지 않는다. 위 테이블은 지표 사전과 현장 조사 기준을 확정한 후 마이그레이션으로 추가한다.
